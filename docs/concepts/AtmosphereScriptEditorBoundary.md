# Atmosphere Script and Editor Boundary

## Purpose

This document defines the intended boundary between manual Flow/Lua atmosphere scripting and Tomb Editor driven object parameter configuration.

The short version:

```text
Manual Flow/Lua: global atmosphere, global weather, wind, sky effects, aurora.
Tomb Editor Object Parameters: local/nullmesh/room/volume atmosphere emitters and detailed effect tuning.
```

This keeps normal level scripts compact while still allowing advanced atmosphere effects through structured editor data.

## Manual Script Scope

Normal level script should stay focused on broad level-wide atmosphere settings.

Recommended manual script use:

```text
- Enable/disable the atmosphere profile.
- Global weather type and strength.
- Global rain/snow quality and budgets.
- Global wind direction and strength.
- Global aurora settings.
- General outdoor atmosphere defaults.
```

Example:

```lua
level.atmosphere = Flow.Atmosphere {
	enabled = true,

	weather = Flow.WeatherProfile {
		type = WeatherType.Rain,
		strength = 0.85,
		quality = WeatherQuality.Auto
	},

	wind = Flow.WindProfile {
		direction = 45,
		strength = 0.6,
		gustStrength = 0.25,
		turbulence = 0.2
	},

	aurora = Flow.AuroraProfile {
		enabled = true,
		intensity = 0.7,
		speed = 0.25
	}
}
```

This is the level-builder-facing script surface.

## Editor-Only / Generated Scope

Local atmosphere emitters should not require builders to write large Lua blocks.

The following should be configured in Tomb Editor through the future Object Parameter System:

```text
- Nullmesh-bound ground fog.
- Local leaf fall emitters.
- Local ash/dust/sand emitters.
- Room-limited mist.
- Volume-limited storm veil effects.
- Per-emitter radius, height, density, colors, generated seed, geometry blocking, and optional texture override.
```

The editor may export these settings to Flow/Lua or runtime metadata, but they should not be presented as the normal hand-written scripting workflow.

Generated exporter output may still use `Flow.AtmosphereEffectProfile` internally:

```lua
Flow.AtmosphereEffectProfile {
	enabled = true,
	type = AtmosphereEffectType.GroundFog,
	scope = AtmosphereEffectScope.Nullmesh,
	anchorName = "fog_pool_01",
	renderMode = AtmosphereEffectRenderMode.Generated,
	radius = 1536,
	height = 256,
	density = 0.8,
	collideWithGeometry = true,
	stopAtWalls = true,
	stopAtFloors = true,
	stopAtCeilings = true,
	clampToRoom = true
}
```

The key point is that this block should be generated by Tomb Editor rather than manually written by most builders.

## Why This Split Matters

A full local atmosphere emitter can require many values:

```text
scope
anchorName
radius
height
density
speed
direction
turbulence
verticalDrift
minSize
maxSize
lifetime
fadeDistance
alpha
renderMode
textureName
generatedDetail
generatedSoftness
generatedVariation
generatedSeed
collideWithGeometry
stopAtWalls
stopAtFloors
stopAtCeilings
clampToRoom
inheritWind
colorA
colorB
```

This is too much for normal scripting. It belongs in a structured editor panel with presets, validation, and grouped beginner/advanced fields.

## Tomb Editor Integration Direction

The Tomb Editor side should use a generic Object Parameter System.

Atmosphere emitters should be only the first major use case. The same system should later be reusable for:

```text
- Sound emitters.
- Light helpers.
- Particle sources.
- Trap settings.
- Puzzle objects.
- Camera helpers.
- AI helpers.
- Plugin-defined object logic.
```

Recommended UI naming:

```text
Object Parameters
```

Recommended atmosphere object naming:

```text
Atmosphere Emitter
Atmosphere Source
Generated Atmosphere Effect
```

Avoid naming the feature `OCB Editor`.

## OCB Role

OCB should remain a compatibility layer and quick-preset fallback only.

Recommended role:

```text
OCB 0   - use default object parameters.
OCB 1   - quick preset 1.
OCB 2   - quick preset 2.
OCB 10+ - legacy compatibility mapping if needed.
```

Complex parameters should not be packed into OCB codes.

## Engine Boundary

TombEngine should not depend on Tomb Editor.

The boundary should be data-based:

```text
Tomb Editor Object Parameters
        ↓ export
Flow.Atmosphere / generated atmosphere metadata
        ↓ runtime
TombEngine AtmosphereController / GeneratedEffectController
```

This keeps both repositories independent and PR-friendly.

## Implementation Notes

For the current TombEngine branch, `Flow.AtmosphereEffectProfile` can remain available as a data shape because Tomb Editor may generate it. It should be documented as advanced/generated data, not as the preferred hand-written builder workflow.

The first renderer implementation should still prioritize global atmosphere and one simple generated layer. Local/nullmesh behavior should be activated only after Tomb Editor can author object parameters cleanly.
